# 二进制帧协议规范（F103RET6 ⇄ ESP32-S3）

> **一句话**：在对等的一对串口之间，用一套**自定帧格式 + CRC16** 可靠地搬 8000 个音频样本和 8 字节判定结果。

---

## 一、为什么要自己定帧格式（而不是直接发原始字节）

**最朴素的做法**是：F103 把 8000 个采样值直接倒进串口，ESP32 收满 8000 字节就开始算。

**问题**：
1. **没有边界** —— 万一中途丢几个字节，ESP32 会把后面的数据整体错位，且**永远无法发现**
2. **无法校验** —— 音频数据错一个字节不会"报错"，只会让特征算歪，表现为"识别率莫名下降"
3. **无法区分类型** —— 音频块、元信息、判定结果混在一起没法分辨

**所以需要一个带帧头 + 长度 + 校验的帧格式**。这是所有工业串口协议的共同做法（Modbus、DL/T645 都一样）。

---

## 二、帧格式

```
┌──────┬──────┬──────┬──────────┬─────────────┬──────────┐
│ SYNC │ CMD  │ SEQ  │   LEN    │   PAYLOAD   │   CRC16  │
│ 0xAA │ 1 B  │ 1 B  │ 2 B (LE) │  LEN 字节    │ 2 B (LE) │
└──────┴──────┴──────┴──────────┴─────────────┴──────────┘
   ▲     └────────┬───────────┘                ▲
   │              │                            │
 帧头         CRC 覆盖范围                  CRC 校验值
（不参与CRC）  （CMD ~ PAYLOAD 全部）
```

| 字段 | 长度 | 说明 |
|---|---|---|
| **SYNC** | 1 B | 固定 `0xAA`，帧起始标志 |
| **CMD** | 1 B | 命令字（见下表）|
| **SEQ** | 1 B | 序号，0~255 循环；用于检测丢帧 |
| **LEN** | 2 B | 载荷字节数，**小端**；范围 0~1024 |
| **PAYLOAD** | LEN | 实际数据 |
| **CRC16** | 2 B | CRC16-Modbus，**小端**；覆盖 `CMD + SEQ + LEN(2) + PAYLOAD` |

**整帧长度** = `LEN + 7`

### ⚠️ 为什么 CRC 不覆盖 SYNC

这是**故意的**：
- SYNC 的作用是"找帧头"，如果 CRC 也覆盖它，那么**滑动找帧头时**每个候选位置都要重算 CRC，逻辑更绕
- 而且 SYNC 是常量，被干扰成一个"非 0xAA 的值"时，接收侧根本走不到 CRC 校验那一步（状态机第一级就把它跳过了）
- **Modbus RTU 的从机地址也不参与 CRC** —— 同样的思路

**代价**：理论上数据区里如果恰好出现 `0xAA`，会被误认成帧头。所以接收侧**必须有第二级防线**（长度合理性 + CRC），见 [§五](#五接收侧的容错设计)。

## 四、载荷布局

### 4.1 `AUDIO_META`（12 字节）

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 4 | `sample_rate` | 采样率，小端（本系统 = 8000）|
| 4 | 4 | `sample_count` | 总采样点数（= 8000）|
| 8 | 1 | `raw_bits` | 原始位宽（= 16，表示 ADC 是 12 位有效）|
| 9 | 1 | `tx_bits` | 传输位宽（= 8，表示压缩到 8 位）|
| 10 | 2 | `reserved` | 保留，填 0 |

**为什么要发 META**：让 ESP32 **不依赖硬编码**就知道"这段数据是多少 Hz、多少点、什么位宽"。
以后如果改成 16 kHz 或 16 bit，只改 F103 侧，ESP32 侧自动适配。

### 4.2 `AUDIO_DATA`（256 字节）

**载荷就是 256 个 8 位量化样本**，顺序 = 采样时间顺序。

**量化方式**：
```c
uint8_t q = (uint8_t)(sample12bit >> 4);    // 12 bit → 8 bit
```

**为什么是 8 位而不是 16 位**（这是个关键取舍）：

| 方案 | 每帧 | 总帧数 | 总字节 | @115200 耗时 | MFCC 质量 |
|---|---|---|---|---|---|
| **16 bit** | 512 B | 16 | 16000 | **1.4 s** | 无损 |
| **8 bit** | 256 B | 32 | 8000 | **0.72 s** | 量化噪声 ≈ −48 dB |

**选 8 位的理由**：
- 语音信号动态范围有限，**12→8 位（除以 16）后信噪比仍有约 48 dB**
- MFCC 关心的是**频谱包络**，量化噪声是白噪声、均匀分布在整个频带，对包络影响很小
- **上传时间减半**是实打实的收益（1.4 s → 0.72 s）

**反量化**（ESP32 侧）：
```c
// 还原到 12 位量纲，并**去直流**
int32_t s = ((int32_t)q - 128) * 16;    // 128 是 8 位中点
```
> ⚠️ 注意这里是 `(q - 128) * 16` 而不是 `q * 16` —— **先减中点再放缩**，
> 否则会在 0 附近产生一个直流偏置，MFCC 的 DCT 第 0 维会被这个偏置污染。

### 4.3 `RESULT`（8 字节）

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | `verdict` | `0x00` = FAIL，`0x01` = PASS |
| 1 | 1 | `confidence` | 置信度 0~100 |
| 2 | 2 | `similarity` | 相似度 ×1000，小端（例：`732` = 0.732）|
| 4 | 4 | `elapsed_ms` | ESP32 侧推理耗时，小端 |

**为什么相似度用 ×1000 的整数**：
- 串口是**字节流**，传浮点要处理 IEEE 754 的字节序和平台差异
- 用 `uint16` 传千分比：**精度到 0.001，足够**，且跨平台无歧义
- 显示时 `732 / 1000 = 0`，`732 % 1000 = 732` → 拼成 `"0.732"`

## 五、接收侧的容错设计

两侧用的是**同一套逻辑**（`uart_proto.c` 和 `uart_link.cpp` 对等实现）。

### 三级防线

```
① 找帧头          ② 长度合理性         ③ CRC16 校验
   滑动搜 0xAA  →  LEN > 1024 ?  →  重算 CRC 比对
                        │                    │
                    不合理 ⇒ 丢弃          不匹配 ⇒ 丢弃
                    继续找帧头             继续找帧头
```

**为什么"长度合理性"是必要的第二级**：
音频数据里出现 `0xAA` 的概率约 **1/256**，每 8 KB 数据平均会出现 **31 次**假帧头。
如果只靠 CRC 过滤，每次都要白等 `LEN` 个字节才能判错 —— 而假的 `LEN` 可能是 60000，
**接收状态机会被卡住几秒**，期间真正的帧全被吞掉。

加上 `LEN > 1024 就直接丢弃` 这一条，**绝大多数假帧头在第二个字节之后就被排除了**。

### 状态机实现

```c
typedef enum { RXS_SYNC, RXS_HEADER, RXS_PAYLOAD, RXS_CRC } RxState;

// 每收到一个字节就喂进来一次（在串口中断回调里，必须快）
void uartRxFeed(uint8_t b) {
    switch (s_rxs) {
    case RXS_SYNC:
        if (b == 0xAA) { s_rxHdrIdx = 0; s_rxs = RXS_HEADER; }
        return;
    case RXS_HEADER:
        s_rxHdr[s_rxHdrIdx++] = b;
        if (s_rxHdrIdx >= 4) {                  // CMD + SEQ + LEN(2)
            s_rxLen = s_rxHdr[2] | (s_rxHdr[3] << 8);
            if (s_rxLen > UART_MAX_PAYLOAD) {   // ★ 第二级防线
                s_rxResync++;  s_rxs = RXS_SYNC;  return;
            }
            s_rxIdx = 0;
            s_rxs = (s_rxLen == 0) ? RXS_CRC : RXS_PAYLOAD;
        }
        return;
    case RXS_PAYLOAD: ...
    case RXS_CRC: ...                            // ★ 第三级防线
    }
}
```

**为什么用"逐字节喂入 + 状态机"，而不是"攒够一帧再解析"**：
- F103 侧接收是**中断驱动、一次只来 1 个字节**（`HAL_UART_Receive_IT` 每次收 1 B）
- 如果在 `HAL_UART_RxCpltCallback` 里干"攒帧 + 解析 + 处理"的活，**中断时间会很长**
- 状态机的方式：中断里只做"喂一个字节"，**几微秒就返回**；
  主循环去查"有没有完整帧了"（`uartResultReady()`）—— 分工清晰，不阻塞

## 六、CRC16-Modbus

### 参数

| 项 | 值 |
|---|---|
| 多项式 | `0xA001`（`0x8005` 的反向表示）|
| 初值 | `0xFFFF` |
| 输入/输出反转 | 是（算法本身已内含）|
| 结果异或 | `0x0000` |
| 覆盖范围 | `CMD + SEQ + LEN(2) + PAYLOAD` |

### 查表实现（两侧一致）

```c
// 256 项查表，字节驱动，每字节 1 次表查询
uint16_t uart_crc16(const uint8_t *data, uint32_t len) {
    uint16_t crc = 0xFFFF;
    while (len--) {
        crc = (crc >> 8) ^ crc_table[(crc ^ *data++) & 0xFF];
    }
    return crc;
}
```

**为什么用查表而不是逐位异或**：逐位算法每个字节要循环 8 次，查表只要 1 次。
在 72 MHz 的 F103 上，逐位算 8 KB 数据约需 **3 ms**，查表只要 **0.4 ms** —— 差别可感知。

**校验向量**（可用于自测）：
```
数据: AA 01 00 08 00 ...
CRC 覆盖: 01 00 08 00 ...
```

## 七、时序与性能

### 一次完整会话的时间线

```
F103                                              ESP32
 │                                                  │
 ├─ [META] rate=8000 pts=8000 bits=16→8  ─────────► │  19 B  ≈1.6 ms
 │                                                  │
 ├─ [DATA] chunk 0  (256 B) ──────────────────────► │  263 B ≈23 ms
 ├─ [DATA] chunk 1  (256 B) ──────────────────────► │
 │  ...                                             │
 ├─ [DATA] chunk 31 ( 64 B) ──────────────────────► │  最后一帧只有 64 个样本
 │                                                  │
 │                              ◄──── [RESULT] 8 B  │  MFCC 56 ms
 │                                                  │
 ├─ 解析结果 → OLED 显示                             │
```

| 阶段 | 耗时 | 计算依据 |
|---|---|---|
| **采集 1 秒音频** | 1000 ms | 8000 点 @ 8 kHz |
| **上传 8224 字节** | **723 ms** | 8224 × 10 bit ÷ 115200 |
| **MFCC + 比对** | **56 ms** | ESP32 实测 |
| **回传 + 解析** | ~2 ms | 8 字节 |
| **端到端合计** | **约 1.3 s** | 采集 + 上传 + 推理 |

> ⚠️ 上传期间 F103 是**阻塞**的（`SendAudioToESP32` 里循环发 32 帧）。
> 这段时间不采音频 —— 但这没问题，因为"这 1 秒已经采完了"。

### 为什么是 115200 而不是更高

| 波特率 | 上传耗时 | 问题 |
|---|---|---|
| 9600 | 8.6 s | 太慢，不可接受 |
| **115200** | **0.72 s** | ✅ 当前选择 |
| 460800 | 0.18 s | ⚠️ 杜邦线长 + 无屏蔽时误码率上升 |
| 921600 | 0.09 s | ⚠️ **实测不可靠**，`crcErr` 明显上升 |

**115200 是"速度 vs 杜邦线可靠性"的平衡点。**
本项目用的是**普通杜邦线**（不是屏蔽双绞线），在这个条件下 115200 已经能跑到 `crcErr=0`。

## 八、实测数据

```
[TX] audio sent: 32 chunks, 8224 bytes
[SUM] bytes=8000/8000  chunks=32/32  took=723ms
[LINK] frames=33 crcErr=0 resync=0 dropped=1
[AUDIO] 8bit: mean=97 min=28 max=165 p2p=137
[AUDIO] ->12bit: mean=1552 min=448 max=2640 p2p=2192
[AUDIO] effective rate = 11065 B/s
```

| 指标 | 值 | 含义 |
|---|---|---|
| `frames=33` | 1 META + 32 DATA | 帧数正确 |
| **`crcErr=0`** | 零 CRC 错误 | 线路质量好 |
| **`resync=0`** | 零重同步 | 没出现过假帧头 |
| **`dropped=1`** | 只丢了 1 帧 | ⚠️ 见下 |
| `effective rate=11065 B/s` | 理论 11520 B/s | 利用率 96%（合理，有帧间隔）|

### 关于 `dropped=1`

**每次都是 1，不是随机丢。** 原因：
- 接收侧统计的是"**序号不连续**"的次数
- 会话开始时 `SEQ` 从 0 重新开始，但接收侧还记着上一次会话的末尾序号
- **所以每次新会话的第 1 帧必然被算作"丢了一帧"**

**这是统计口径问题，不是真的丢数据** —— `bytes=8000/8000` 证明数据完整。
（如果要修，就在会话开始时复位序号基准；当前为了"能看出真丢帧"故意保留了这个行为。）

## 九、这份协议的可复用点

面试时如果被问"你还懂什么通信协议"，可以讲：

1. **它能证明你理解"帧同步"的本质** —— 为什么需要帧头、长度、校验三层
2. **你能自己算性能** —— 8224 字节 @115200 为什么是 723 ms
3. **你做的是"对等实现"** —— 两侧同一套状态机，出问题排查思路能复用
4. **你考虑了对抗性场景** —— 数据里出现 0xAA 怎么办（假帧头）、LEN 被干扰怎么办（卡死）
