# 演示视频脚本与录制指南
## 项目：双 MCU 声纹识别门禁系统（毕设升级版）

> **目标**：用 2~3 分钟视频证明「这个东西真的能做出来、能跑通」。
> **核心原则**：**先给结果，再讲原理**。面试官/HR 看视频前 20 秒就决定要不要继续看。

---

## 〇、录制前的硬件清单（务必逐项确认）

| # | 设备 | 状态 | 备注 |
|---|---|---|---|
| 1 | STM32F103RET6 核心板 | 上电、已烧最新固件 | OLED 显示正常 |
| 2 | ESP32-S3（N16R8） | 上电、已烧 voicelock 固件 | 串口能看到日志 |
| 3 | MAX9814 麦克风模块 | 接 PA1 + 3.3V + GND | GAIN 接 GND（60dB）|
| 4 | OLED SSD1306 | 接 PB6/PB7 + 3.3V + GND | **画面主角，别挡住** |
| 5 | USB-TTL（CH340）| 接 PA9/PA10 | 看 F103 日志 |
| 6 | **两个串口窗口** | COM8（F103）+ COM6（ESP32）| 字号调大，方便录屏 |

### 接线（三根关键线，接错就演示不了）

```
F103 PB10 (TX)  ──►  ESP32 IO7  (RX)     音频上行
F103 PB11 (RX)  ◄──  ESP32 IO6  (TX)     判定回传   ← 最容易漏
F103 GND        ───  ESP32 GND           共地
```

### 录制前必做：确认 ESP32 里已注册好你的声纹

```
ESP32 串口敲 S
→ 应该看到：enrolled=1  count=3~5/5  threshold=0.52  sigma2=...
```

**⚠️ 如果 `count=0`，先做一遍注册**（见下面"附录 A"）。

## 一、分镜脚本（总时长 2~3 分钟）

### 镜头 1｜开场：系统全貌（15 秒）

| 项 | 内容 |
|---|---|
| **画面** | 三个设备摆在一起：F103 板 + ESP32 板 + 麦克风 + OLED |
| **镜头** | 手机横屏，离 40cm，缓慢平移扫过整个桌面 |
| **字幕** | 双 MCU 声纹识别门禁系统 · STM32F103RET6 + ESP32-S3 |
| **旁白** | "这是一个双 MCU 协作的声纹识别门禁系统。STM32 负责实时音频采集，ESP32-S3 负责声纹特征提取和比对。" |

> 💡 **要点**：开场必须有"设备全景"，让观众知道这是**实物**不是仿真。

---

### 镜头 2｜上电启动（15 秒）

| 项 | 内容 |
|---|---|
| **操作** | 按 F103 复位键 |
| **画面** | ① 串口滚动打印 `[BOOT]` 日志 ② OLED 亮起显示待机界面 |
| **镜头** | 先拍串口日志（3 秒），再切到 OLED 特写（5 秒）|
| **字幕** | 8kHz 音频采集启动（TIM2 → ADC → DMA）· I2C OLED 就绪 |

**串口应该出现**：
```
[BOOT] uart it ok
[AUDIO] 8kHz capture started (TIM2 -> ADC1 -> DMA)
[BOOT] all init done
```

**OLED 应该显示**：
```
 VOICE LOCK V2
 D:CLOSE W:NO
 A: 512
 R:BOOT
```

> 💡 **要点**：展示"上电自检通过"，证明系统稳定。

---

### 镜头 3｜⭐ 本人通过（40 秒）—— **视频的高潮**

| 项 | 内容 |
|---|---|
| **操作** | ① ESP32 串口敲 `V` ② F103 串口敲 `U` ③ **对着麦克风说一句话** |
| **画面** | **OLED 特写为主**，串口日志用画中画 |
| **镜头** | 固定机位对着 OLED，**不要晃** |
| **字幕** | 声纹验证 → 相似度 0.637 > 阈值 0.52 → **允许通行** |

**OLED 应该显示（停留 10 秒，足够拍清）**：
```
┌──────────────────┐
│  *** PASS ***    │   ← ★ 必须拍清楚这一行
│  SIM:0.637       │
│  ACCESS GRANTED  │
│  R:PASS          │
└──────────────────┘
```

**F103 串口**：
```
=== VOICEPRINT VERIFY (8kHz) ===
[CAP] baseline=1563 noise_rms=44 thresh_rms=150
[CAP] voice triggered, capturing 1s ...
[CAP] uploading to ESP32-S3 ...
[CAP] waiting for verdict ...
[RES] verdict=PASS confidence=63 sim=0.818 esp_took=56ms
[RES] === ACCESS GRANTED ===
```

**ESP32 串口**：
```
[SPK] similarity = 0.6372  (threshold 0.52)  => PASS
[SUM] == PASS ==  sim=0.637  (sent to F103)
[LINK] frames=66 crcErr=0 resync=0
```

> 💡 **要点**：
> - 从"敲 U"到"屏幕显示 PASS"**只要约 1.3 秒**（采集 1s + 上传 0.72s + 推理 56ms）——
>   **录的时候可以不剪辑，让观众看到实时速度**，这是加分项。
> - 说话时**离麦克风 25~30cm，正常音量**（太近会削顶影响相似度）。

---

### 镜头 4｜⭐ 他人被拒（30 秒）—— **安全性证明**

| 项 | 内容 |
|---|---|
| **操作** | F103 敲 `U`，**用手机播放另一段人声**（或让家人/朋友说）|
| **画面** | OLED 特写 |
| **镜头** | 同上，固定机位 |
| **字幕** | 他人语音 → 相似度 0.49 < 阈值 0.52 → **拒绝通行** |

**OLED 应该显示**：
```
┌──────────────────┐
│  --- FAIL ---    │   ← ★ 对比镜头 3
│  SIM:0.486       │
│  ACCESS DENIED   │
│  R:FAIL          │
└──────────────────┘
```

> 💡 **要点**：
> - **必须用"别人的声音"**，最好是**异性**或**音色差异大**的，区分度更明显。
> - 手机播放时**音量放大些**，但要离麦克风 20cm 左右。
> - **和镜头 3 形成对比**是这段的全部意义 —— 剪辑时把两段并排或紧挨着放。

---

### 镜头 5｜技术亮点：交叉验证矩阵（25 秒）

| 项 | 内容 |
|---|---|
| **操作** | ESP32 串口敲 `X` |
| **画面** | 串口输出特写 |
| **字幕** | 同一人 5 段录音的模板一致性 0.83~0.88 |

**串口应该出现**：
```
---- TEMPLATE CROSS CHECK ----
        #0      #1      #2
  #0   1.000   0.830   0.879
  #1   0.830   1.000   0.850
  #2   0.879   0.850   1.000
  worst self-similarity (off-diagonal) = 0.830
```

> 💡 **要点**：这段证明"算法不是玄学" —— **同一个人的多段录音确实高度相似**，
> 而不同人明显更低。**用数据说话**比讲原理更有说服力。

### 镜头 6｜技术亮点：完整算法栈（20 秒）

## 二、视频规格建议

| 项 | 建议 |
|---|---|
| **时长** | **2~3 分钟**（超过 3 分钟没人看完）|
| **分辨率** | 1080p / 60fps（拍 OLED 时帧率高一点更清楚）|
| **横屏** | ✅ 用横屏（竖屏在电脑上看很难受）|
| **剪辑** | **尽量少剪辑**，保留真实操作节奏（可信度更高）|
| **字幕** | ⭐ **必须加字幕**（HR 经常静音看）|
| **背景音乐** | 可选，音量压低（-25dB 左右），别盖过旁白 |
| **文件名** | `声纹门禁系统_演示视频.mp4` |

## 三、录制技巧（血泪经验）

### ✅ 一定要做

| 项 | 原因 |
|---|---|
| **拍 OLED 时手机固定** | 手持会糊，OLED 字小，糊了就白拍 |
| **串口窗口字号调到 16+** | 默认字号录出来看不清 |
| **关掉串口的时间戳** | 省空间，画面干净 |
| **先试录 20 秒回看** | 确认 OLED 不反光、串口能看清 |
| **说话前等 OLED 显示 `LISTENING`** | 否则可能没触发 VAD |

### ❌ 千万别做

| 项 | 原因 |
|---|---|
| 边录边改代码/接线 | 中途出错会毁掉整段素材 |
| 说话时贴近麦克风（< 10cm）| **会削顶**，导致相似度掉到 0.5 左右，可能被误拒 |
| 用同一段录音既做注册又做验证 | 那是自欺欺人，且相似度会异常高（>0.95）|
| 视频里出现真实姓名/学号 | 隐私 |

## 四、常见翻车点与对策

| 现象 | 原因 | 对策 |
|---|---|---|
| 敲 `U` 后没反应 | VAD 没触发（说话太轻/太远）| 靠近一点、说响一点，看到 `voice triggered` 再继续 |
| OLED 显示 `NO_RES` | **PB11 ← IO6 回传线没接** | 检查那根线，重新插紧 |
| OLED 显示 `NO_VOICE` | 10 秒内没检测到语音 | 敲 `U` 后**立刻**说话 |
| 自己说也被判 FAIL | 相似度偏低（< 0.52）| 见"附录 B：相似度偏低怎么办" |
| 他人说也被判 PASS | 区分度不够 | 换音色差异更大的人声 |
| 屏幕中途黑掉 | 电压跌落 | 已加显示看门狗（每 2 秒自动恢复）；同时换更好的 USB 线/口 |
| 串口全是乱码 | 波特率不对 | 确认 115200 |

## 附录 A：重新注册声纹（如果 `S` 显示 count=0）

```
ESP32 串口：
  C          ← 清空旧模板
  E          ← 进入注册模式

F103 串口：
  U          ← 说一句话（保持同样距离/音量）
  U          ← 再说一句
  U          ← 再说一句
  U          ← 再说一句
  U          ← 再说一句（共 5 次）

ESP32 串口：
  X          ← 看交叉验证矩阵，worst self 应该 > 0.80
  S          ← 确认 count=5
```

**⚠️ 注册时最容易犯的错**：5 次说话的距离/音量不一致 → 模板本身就散 → 验证必然不稳。
**建议**：坐着不动，麦克风固定位置，每次都正常音量说完。

---

## 附录 B：相似度偏低怎么办

**先判断是"注册质量差"还是"说话条件不一致"**：

| 检查 | 命令 | 期望 |
|---|---|---|
| 模板自身一致性 | ESP32 敲 `X` | worst self-similarity **> 0.80** |
| 本次说话是否削顶 | F103 看 `[CAP] min=` | **不能是 0** |

**如果 `min=0`（削顶）** → 说话太响/太近 → 退到 25~30cm，正常音量

**如果 worst self < 0.80** → 注册质量差 → 重新注册（附录 A）

**如果都不对，且自己稳定在 0.55~0.60** → 适当降低阈值：
```
ESP32 敲 T0.52    （或 T0.50）
```
**⚠️ 但不要低于 0.50** —— 否则他人的 0.49~0.52 也可能通过。

## 附录 D：这套系统的技术要点（面试时可能被追问）

**如果面试官看视频后问"这是怎么做的"，按这个顺序答**：

1. **架构**：为什么用双 MCU？
   > "F103 没有 FPU，跑 FFT 很吃力；ESP32-S3 有 240MHz 双核，适合做特征提取。
   > 所以让 F103 专注实时采集（硬件定时器触发 ADC + DMA，不占 CPU），
   > ESP32 专注算法。这样职责清晰，也避免了一个芯片既要实时又要算力的问题。"

2. **采集**：8kHz 怎么保证准确？
   > "用 TIM2 的比较输出触发 ADC，硬件触发不依赖软件定时，实测 7996~8000Hz。"

3. **VAD**：怎么判断"有人在说话"？
   > "按 10ms 分帧算 RMS 能量。阈值取噪声底的 1.5 倍，
   > 噪声底用**最小值统计法**估计 —— 取最近 10 帧的最小值，
   > 这样即使正在说话，噪声底也不会被语音污染。"

4. **特征**：MFCC 怎么算的？
   > "预加重 → 25ms 分帧（10ms 步进）→ 汉明窗 → 256 点 FFT（自己写的
   > 基 2 迭代实现）→ 26 个 Mel 三角滤波器 → 取对数 → DCT 得到 14 维。
   > 再加上一阶、二阶差分共 42 维，最后对每一维取**均值和标准差**，
   > 得到 84 维的超矢量。"

5. **比对**：相似度怎么算的？
   > "全局 z-score 归一化 → 加权欧氏距离 → 高斯核映射到 0~1。
   > 关键是 **σ 自动标定**：用注册样本两两距离的中位数反解 σ²，
   > 让'本人的正常波动'对应 0.85 左右，这样每个人的尺度都是自适应的，
   > 不需要手工调参。"

6. **踩坑**（**这段最能加分**）：
   > "算法我迭代了 5 版。第一版直接用 MFCC 余弦相似度，结果被能量维度主导 ——
   > 不同内容的信号相似度都有 0.73。第二版加了逐样本 z-score，
   > 结果同一个人变成**负相似度** —— 因为'减均值'把说话人的个性信息减掉了。
   > 第三版加倒谱均值归一化，又和帧平均操作冲突……
   > 最后定位到：**归一化必须在全局统计量上做，不能每段自己做**。"

7. **如果被问"和讯飞 API 比怎么样"**：
   > "本地方案的相似度区分度在 0.2 左右（本人 0.6~0.73，他人 0.49~0.52），
   > 不如云端 API 精确，但**完全离线、响应 1.3 秒、零调用成本**，
   > 适合对隐私和联网稳定性敏感的场景。两者可以组合成两级验证。"
