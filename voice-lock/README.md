# 双 MCU 声纹识别门禁系统 · 端侧全离线声纹验证

> **STM32F103RET6（8 kHz 实时采集 + VAD）** ⇄ UART 二进制协议 ⇄ **ESP32-S3（MFCC + 声纹比对）** ⇄ OLED
>
> 状态：**已完成并实测通过**。本人语音通过 / 他人语音拒识，单次验证端到端约 **1.3 秒**，**全流程离线、不依赖任何云端 API**。

---

## 一、这是什么（一句话）

对着麦克风说一句话，系统判断"**是不是本人**"，在 OLED 上显示 `*** PASS ***` 或 `--- FAIL ---`。

**和普通"语音识别"的区别**：它不关心**你说了什么**，只关心**是谁在说** —— 这叫**声纹识别（Speaker Verification）**。

---

## 二、和毕业设计的区别（为什么叫"升级版"）

原毕设（见 [`../archive/thesis-original-C8T6/`](../archive/thesis-original-C8T6/)）的架构是：

```
STM32F103C8T6 ──ADC轮询采集──> 13 维时域统计特征 ──ESP8266──> Python 服务器判定
```

**问题**：
- 采集是**软件轮询**，采样率不稳定
- 特征只有 13 维时域统计量（均值/最值/峰峰值/8 段能量），**对说话人区分能力很弱**
- 判定**依赖网络 + 服务器**，断网就用不了
- 而且实际上"服务端算法"是**讯飞 WebAPI**，自己并没有实现声纹识别

**升级后**：

| 维度 | 原毕设 | 升级版 |
|---|---|---|
| **架构** | 单 MCU + 云 | **双 MCU（采集/算力分离）** |
| **采样** | ADC 软件轮询 | **TIM2 硬件触发 + DMA**，实测 7996–8000 Hz |
| **触发** | 单点阈值 | **帧能量 VAD + 最小值统计法估噪声底** |
| **特征** | 13 维时域统计量 | **84 维 MFCC 超矢量（含 Δ/ΔΔ）** |
| **算法** | 调讯飞 API | **按标准流程自己实现**：FFT、Mel 滤波器组、DCT、比对 |
| **判定** | 云端 Python / WebAPI | **端侧高斯核 + σ 自动标定** |
| **网络** | 必需 | **完全不需要** |
| **延迟** | 网络往返 | **1.3 秒** |

> **诚实说明**：升级版是**独立的端侧方案**，不复用原毕设的服务器代码。
> 论文里的"端云协同 + 讯飞 API"仍可作为**扩展路径**（两级验证：本地粗筛 + 云端精确），
> 但主线已经是本仓库这套离线实现。

## 三、系统架构

```
┌──────────────────────────────┐         ┌──────────────────────────────┐
│   STM32F103RET6              │         │   ESP32-S3 (N16R8)           │
│   【采集节点】                │         │   【声纹引擎】                │
│                              │         │                              │
│  MAX9814 ──► PA1 (ADC1_IN1)  │         │  ① 收帧 + CRC16 校验          │
│              │               │         │  ② 8bit → 12bit 反量化        │
│              ▼               │         │  ③ MFCC 特征提取              │
│  TIM2_CH2 硬件触发 @8kHz     │   UART  │     预加重→分帧→汉明窗         │
│              │               │  115200 │     →自写FFT→Mel→log→DCT      │
│              ▼               │ ──────► │  ④ 84 维超矢量                │
│  ADC1 + DMA 循环缓冲          │  PB10   │  ⑤ 与模板比对（高斯核）        │
│  (16384 点滚动)              │  →IO7   │  ⑥ 判定 PASS / FAIL           │
│              │               │         │                              │
│              ▼               │ ◄────── │  ⑦ 回传结果                   │
│  帧能量 VAD 语音触发          │  PB11   │                              │
│              │               │  ←IO6   │                              │
│              ▼               │         └──────────────────────────────┘
│  取 1 秒音频（8000 点）       │
│              │               │
│              ▼               │
│  8bit 量化 → 分 32 块上传     │
│              │               │
│              ▼               │
│  等判定 → OLED 显示结果       │
│  PB6/PB7 (I2C1) ──► SSD1306  │
└──────────────────────────────┘
```

**为什么用双 MCU**（面试必问）：

1. **F103 没有 FPU**，跑 256 点 FFT + 26 个 Mel 滤波器很吃力；
   ESP32-S3 是 240 MHz 双核 + 硬件浮点，做特征提取只要 **56 ms**
2. **职责分离**：F103 端"实时性优先"（硬件定时器触发采样，全程不占 CPU），
   ESP32 端"算力优先"，两边互不干扰
3. **可替换性**：以后把 ESP32 换成更强的芯片，F103 端代码一行不用改

## 四、接线

| F103RET6 | 方向 | ESP32-S3 | 作用 |
|---|---|---|---|
| **PB10** (USART3_TX) | → | **IO7** (UART2 RX) | 音频上行 |
| **PB11** (USART3_RX) | ← | **IO6** (UART2 TX) | 判定回传 ⚠️ 最易漏 |
| **GND** | — | **GND** | **必须共地** |

| F103RET6 | 器件 | 说明 |
|---|---|---|
| **PA1** (ADC1_IN1) | MAX9814 `OUTPUT` | 麦克风模拟输出 |
| 3.3V / GND | MAX9814 `VDD` / `GND` | 供电 |
| GND | MAX9814 `GAIN` | 接 GND = **60 dB 最大增益** |
| 悬空 | MAX9814 `A/R` | — |
| **PB6 / PB7** | OLED `SCL` / `SDA` | I2C1，地址 0x78（7 位 0x3C）|
| **PA9 / PA10** | USB-TTL `RXD` / `TXD` | 调试串口，115200 |
| PA13 / PA14 | DAP-Link | SWD 烧写 |

**电源**：两块板**各自用独立 USB 供电**，只共地。
（曾试图共用一路，音频采集 + 串口突发时电流骤增导致 OLED 掉显示，见 [§八.3](#八踩过的坑)。）

**⚠️ PB0 上的跳帽**：原来用于舵机 PWM（TIM3_CH3）。本项目改用 OLED 做指示，
**舵机已弃用**，PB0 保持空闲即可。

## 六、怎么编译

### 采集节点（STM32F103RET6）

**工具**：Keil MDK 5.37+ （需要 **ArmClang / AC6** 编译器）

```
1. 打开 voice-lock/firmware-stm32-ret6/MDK-ARM/MyBiye.uvprojx
2. Options for Target → Target → ARM Compiler 选 "compiler version 6"
3. Rebuild
4. DAP-Link 烧写（Flash 算法选 High-density 512k！）
```

**⚠️ 已知编译坑**（都是实际踩过的）：
- **MDK-Lite 有 32 KB 代码上限**，本项目约 44 KB → **必须用社区版或更高**
  （ArmClang 编译出来 37764 B Code + 6568 B RO-data ≈ 44 KB）
- **器件包**：需要 `Keil.STM32F1xx_DFP`（2.3.0 即可）
- **不要用 CubeMX 重新生成**：会覆盖手写代码（`audio_capture.c` / `uart_proto.c` 等都是手写的）

### 声纹引擎（ESP32-S3）

**工具**：PlatformIO（VSCode 插件或命令行）

```bash
cd voice-lock/firmware-esp32-voicelock
pio run                 # 编译
pio run -t upload       # 烧写（先改 platformio.ini 里的 upload_port）
pio device monitor -b 115200
```

**关键配置**（`platformio.ini`）：
```ini
board_build.arduino.memory_type = qio_opi     # N16R8 是 Octal PSRAM，配错起不来
build_flags = -DARDUINO_USB_CDC_ON_BOOT=0     # 日志从 CH343 口出
```

## 七、怎么用

### 串口命令（F103 侧，115200）

**大小写都认**（早期版本只认小写，是个真实 bug，见 [§八.4](#八踩过的坑)）。

| 命令 | 作用 |
|---|---|
| **`U`** | ⭐ **完整门禁流程**：采集 → 上传 → 等判定 → OLED 显示 |
| `P` | 只上传、不等判定（链路测试用）|
| `T` | 音频采集自检（不带触发/上传）|
| `K` | 声学标定（测静音 vs 说话的 RMS）|
| `X` | USART3 硬件诊断（TX 通路）|
| `L` | USART3 回环测试（需短接 PB10↔PB11）|
| **`D`** | ⭐ **I2C / OLED 总线诊断**（扫描 0x08~0x77）|
| `O` / `C` | 开锁 / 关门（手动）|
| `H` | 帮助 |

### 串口命令（ESP32 侧，115200）

| 命令 | 作用 |
|---|---|
| **`E`** | 注册模式（进入后每收到一段音频就存一个模板）|
| **`V`** | 验证模式 |
| **`X`** | 模板交叉验证矩阵（看自己 5 段的一致性）|
| **`S`** | 打印状态（模板数、阈值、σ²）|
| `C` | 清空所有模板 |
| **`T0.52`** | 设置阈值（示例：0.52）|
| `M` | MFCC 自检（自比应 = 1.0000）|
| `H` | 帮助 |

### 典型流程

```
ESP32: C                清空
ESP32: E                注册模式
F103 : U  × 5           说 5 次（保持同样距离/音量）
ESP32: X                看交叉矩阵（worst self 应 > 0.80）
ESP32: T0.52            设阈值
ESP32: V                验证模式
F103 : U                说一句 → OLED 显示 PASS
F103 : U                放别人的声音 → OLED 显示 FAIL
```

## 八、踩过的坑

> 这一段是**最有价值的部分** —— 面试官最想听的往往不是"做成了什么"，
> 而是"**卡在哪里、怎么定位出来的**"。

### 1. 算法迭代 5 版才找到正确的归一化方式

| 版本 | 做法 | 结果 | 失败原因 |
|---|---|---|---|
| v1 | 原始 MFCC 余弦相似度 | 不同内容也有 0.73 | **被能量维度主导** —— 大声说话就"像" |
| v2 | 逐样本 z-score | **同一个人 −0.76** | **减均值把说话人个性信息减掉了** |
| v3 | 加权 + L2 归一化 | 本人 0.99，但视频也 0.994 | 区分度消失 |
| v4 | CMN（倒谱均值归一化）+ 帧平均 | 特征全为 0.00 | **CMN 和帧平均互斥** —— 先减均值再平均，等于双重减均值 |
| **v5** | **均值 + 标准差超矢量 + 全局 z-score** | **本人 0.59~0.73 / 他人 0.49~0.52** | ✅ 有效 |

**核心结论**：
> **归一化必须基于"所有注册样本的全局统计量"，不能每段自己算。**
> 因为"每段自己减均值"会同时抹掉**说话人之间的差异**和**说话人内部的差异** ——
> 而恰恰是前者构成了声纹。

详见 [`docs/algorithm.md`](docs/algorithm.md)。

### 2. σ 拍脑袋设错，导致自己只有 0.40 相似度

高斯核 `exp(-d²/(2σ²))` 里的 σ² 一开始硬编码成 `MFCC_FEAT_DIM = 84`，
但实测距离 d² ≈ 350 —— **差了一个数量级**，导致所有人的相似度都被压到 0.4。

**修法**：**自动标定**。让"本人的正常波动"对应 0.85 相似度：

```c
σ² = median(两两模板距离) / (-2 · ln(0.85))
```

**好处**：每个人的特征离散度不同，σ 自动适配，**不需要人工调参**。

### 3. OLED 突然黑屏，但 I2C 统计显示 `err=0`

**现象**：跑端到端测试时屏幕全黑，按复位又恢复。

**诊断过程**：
1. 加了 I2C 错误计数 → `total ok=1079 err=0`
2. **`err=0` 是关键证据** —— 数据一直成功发出去了
3. 那问题不在通信，在**屏幕自己掉了显示**

**根因**：音频采集（ADC+DMA 全速）+ ESP32 高速串口收发让电流骤增 →
电压瞬间跌落 → **SSD1306 内部的 Display ON 寄存器被复位**。
而 STM32 板上有电容撑着，主程序毫无察觉继续发数据。

**修法**：**显示看门狗** —— 每 2 秒重发一次"配置 + 开显示"命令
（`SSD1306_Reinit()`）。屏幕正常时无副作用，掉了就立刻恢复。

**另一个发现**：原来的 `OLED_Init()` **完全没检查 I2C 返回值**，
失败了也打印 "OLED ok" —— 这就是"屏幕黑但毫无线索"的根源。

### 4. 敲大写命令没反应（真实 bug）

```c
switch (c)          // c 是原始字符
case 'a':           // 只匹配小写！
```

**所有人都会自然地去敲大写**（`S`、`D`、`L`），结果全落到 `default` 报 unknown。
修法：统一 `toupper()` 归一化，case 标签全大写。

> **这个 bug 特别隐蔽** —— 表现为"我明明烧写了新固件，但新命令不认"，
> 会让人误以为是烧写失败，浪费大量时间。

### 5. 舵机嗡嗡响但不动 → 最终弃用

- 信号线颜色无标识（红/橙/黑），只能靠惯例猜
- PB0 上有跳帽，拔掉才能用
- 寄存器诊断证明 PWM 配置**完全正确**（`CEN=1`、50 Hz、`PB0=AF_PP`）
  → 说明问题在**片外**（舵机本身或接触）
- 上电有嗡嗡声但不动作 = 典型"通电但控制信号没生效"

**决策**：在时间有限的情况下，**改 OLED 显示**。
"允许通行 / 拒绝"的语义完全等价，且 OLED 全程稳定工作、零额外硬件。
**工程判断：把资源投向确定能做出来的方案。**

### 6. RGB 灯模块插针太松 → 也弃用

一度想用 WS2813E 可寻址 RGB 灯（绿=通过/红=拒绝）代替舵机，好处是电流小、免独立电源。
但拿到实物发现**模块用 JST-XH 4P 插座，插针非常松，一碰就掉** —— 演示不可靠。
而舵机的 3P 杜邦母头反而插得很紧。

> **"接插件可靠性"是选型时容易忽略、但实际很关键的因素。**

### 7. RGB 用 PA4 而非 PB0

核心板 P3 排针上 PB0/PB1 默认接着跳帽，会把信号短路或钳位。
与其去动跳帽（不确定是否兼顾启动模式），不如换个确定空闲的引脚 ——
**改一行代码的成本远低于排查跳帽**。

### 8. 说话太大声会削顶，导致相似度暴跌

`[AUDIO] min=0` 说明撞到 ADC 下限。
削顶会扭曲 MFCC 特征（`dim1` 从 155 跳到 195），相似度从 0.70 掉到 0.49。

**用法要求**：**离麦克风 25~30 cm，正常音量**。
根因是 MAX9814 的 `GAIN` 接 GND = 60 dB 最大增益；
如果经常削顶，把 `GAIN` 改接 3.3V（50 dB）即可，但要**重新注册模板**。

## 九、实测结果

| 项目 | 结果 | 怎么测的 |
|---|---|---|
| **采样率** | **7996–8000 Hz** | 串口 `[CAP]` 打印实测值 |
| **上传完整性** | 32/32 块，**`crcErr=0`** | ESP32 `[LINK]` 统计 |
| **上传耗时** | **723 ms** | 8224 字节 @115200 |
| **MFCC 耗时** | **56 ms** | ESP32 `[MFCC]` 打印 |
| **MFCC 自检** | 自比 **1.0000** / 互比 **0.7319** | `M` 命令 |
| **模板一致性** | **0.830 ~ 0.879**（同人 3 段）| `X` 命令 |
| **本人相似度** | **0.59 ~ 0.73** | `V` 模式实测 |
| **他人相似度** | **0.49 ~ 0.52** | 多人说话视频 |
| **区分度** | **约 0.2** | 两者之差 |
| **端到端延迟** | **约 1.3 秒** | 采集 1 s + 上传 0.72 s + 推理 56 ms |
| **代码量** | Code 37764 B + RO 6568 B ≈ **44 KB** | Keil Build Output |
| **RAM** | 55248 B / 64 KB（**84%**）| Keil Build Output |

**Flash 只占 512 KB 的 8.7%，RAM 占 84%（主要是 16384 点 DMA 缓冲 = 32 KB）。**

## 十、这个项目能证明什么

面试时可以这样定位：

| 能力 | 证据 |
|---|---|
| **底层驱动** | 定时器硬件触发 ADC + DMA 循环缓冲、I2C + SSD1306、UART 中断收发 |
| **通信协议设计** | 自定义二进制帧（帧头/序号/长度/CRC16）、非阻塞收帧状态机、双侧对等实现 |
| **数字信号处理** | 自写基 2 迭代 FFT、Mel 滤波器组、DCT-II、预加重、差分系数 |
| **算法工程能力** | **5 轮迭代定位归一化缺陷**、σ 自动标定、区分度量化验证 |
| **调试方法论** | 用寄存器读值区分"配置错"vs"片外问题"；用 `err=0` 反证通信正常 |
| **工程取舍** | 舵机→OLED、RGB→OLED，**接插件可靠性**与**时间成本**的权衡 |
