## 1. 一句话概括

**双 MCU 工业物联网网关**：STM32F411 做实时采集与执行（Modbus RTU 从机），
ESP32-S3 做协议网关 + 本地 HMI + 端侧 AI 推理（Modbus 主站），
通过 RS485 两线半双工总线互联；本地带 SPI 彩屏 + OLED 双显示，
推理结果在 <400µs 内给出，总线首试成功率 **100%**。

**技术关键词**：Modbus RTU 主从协议栈（手写）、RS485 半双工时序、
FreeRTOS 多任务与核间分工、LVGL + 自建中文字库、TFLite Micro 端侧推理、
看门狗分级、总线可靠性工程。

**分工原则（面试考点）**：**节点只管"采得准"，网关管"看得懂"。**

- 节点算力/内存有限，跑不动模型
- 模型更新只需动网关一台，不用刷所有节点
- 总线带宽足够传原始值（600 点窗口 @115200 约 23ms）

## 4. 关键技术问题与解法（★ 面试主打部分）

### 4.1 总线首试成功率 58% → 100%（最重要的一个）

**现象**：485 通信约 42% 的请求第一次失败，且 `重试数恒等于超时数`
—— 即"**首试必失败、重试必成功**"，100% 复现。

**排查过程（含 3 次走错方向，这才是价值所在）**：

| 假设 | 实验 | 结果 |
|---|---|---|
| 位速率电气裕量不足 | 115200 → 9600 | 改善（26%→63%）但**仍有 42% 失败** |
| 需要 120Ω 终端电阻 | 加电阻 | **58.2% → 52.6%，毫无改善** ✗ |
| 从机应答慢 | 超时 400 → 700ms | 重试数不变 ✗ |
| 主站 DE 切回时机 | 加 `rx_drain()` | 59.6%，几乎无变化 ✗ |
| A/B 相位反 | 对调 A/B | 彻底离线 → 原接法正确 ✗ |

**突破点：写了双口对账工具**（`tools/measure_bus_pair.ps1`）
**同时**抓主站和从站，用**增量**对比：

```
主站发送尝试 176 次
从站收到请求 100 个      ← 少了 76 次！
从站静默丢弃 0           ← 收到的全应答了
主站收到响应 102
```

**"从站只收到 100 个请求，却正好对应主站收到的 102 个响应"**
—— 这两个数字吻合得太好，证明**丢的是"请求方向"**，不是"响应回不来"。

> 💡 关键方法论：**只盯一侧日志永远查不出"对端有没有收到"。**
> 而且必须用**增量**对比 —— 两侧计数器是各自累计的，运行时长不同，
> 直接比绝对值会得出"从站收到 29245 个请求、主站只发了 3008 个"这种荒谬结论
> （我一开始就被它误导过）。

**根因**：从机发送响应时会关掉接收器（DIR 拉高 → 模块内 `~RE` 同时拉高），
要等 **TC 标志**（最后一字节移出移位寄存器）才放开总线并重新武装 UART 接收。
主站间隔不够就发下一个请求 → **整帧被静默丢弃**；等超时后重试时从机已就绪
→ **必然成功**。

**解法**：`MODBUS_TXN_GUARD_US` 从事务后 100ms 提到 **400ms**（固定值）。

**再踩一个坑**：我一开始把它写成**与波特率成比例**（`125 × T35`），
9600 下是 500ms（好用），切 115200 后变成 **42ms → 立刻退回 50% 失败**。
因为要覆盖的是**从机的固定开销**（RTOS 调度 + 响应构建 + 重新武装接收），
**它不随波特率缩小** ⇒ 必须按绝对时间给。

**结果**：`TX == RX，超时 0、重试 0、CRC错 0`（870 次事务）。

**这个故事能体现的能力**：假设-实验-反证的完整闭环；被错误结论误导后
如何用**新工具**（双口对账）跳出；以及"降速有效 ≠ 根因是位速率"这种
**相关不等于因果**的判断。

### 4.2 假超时：从机明明回了，主站却说超时

改完间隔后出现新问题：**快车道读窗口头恒定失败**，但慢车道读数 100% 成功。

**定位**：我加的诊断日志打出了**具体状态码**：
```
[快车道] 窗口读失败（累计 成功 0 / 失败 11）：读窗口头失败（状态码 1）
```
`状态码 1 = MB_ERR_TIMEOUT` —— 这个细节把方向从"通信问题"扭到了"预算问题"。

**根因**：主站同步等待用 `ulTaskNotifyTake()`，其**等待预算**按
`(排队深度+1) × MODBUS_MAX_SINGLE_REQ_MS + SLACK` 算。
我把 `MODBUS_MAX_SINGLE_REQ_MS` 从 1000 降到 200 时，**漏算了 400ms 的
事务间隔也是单次请求耗时的一部分**：

```
真实单请求最坏耗时 ≈ (间隔400 + 传输23 + 驱动开销25) × 3次尝试 ≈ 1344ms
而我给的预算 = (0+1)×200 + 150 = 350ms（还被上限封到 600）
```

⇒ 预算比一次请求的真实耗时还短 → **提前返回假超时**。

**解法**：`MAX_SINGLE_REQ_MS` 200→600、`NOTIFY_BUDGET_MAX_MS` 600→1500。

**为什么这个坑值得讲**：总线侧一切正常（超时 0、CRC错 0）、
从机侧也一切正常（`parse0` 冻住不动），**两侧都"健康"但功能不通** ——
这类"假故障"比真故障难查得多，靠的是**把内部状态打出来**而不是继续猜。

### 4.3 没有触摸屏也没有按键，怎么操作界面？

触摸那 5 根线当初特意没接（省 5 个引脚 + 免校准），按键也没焊。
于是三页界面**切不了**。

**解法**：三个入口 + 一条线程安全红线：

| 入口 | 实现 | 用途 |
|---|---|---|
| **自动轮播** | 10 秒切一页 | 无人值守时自己展示 |
| **串口命令** | `console.cpp`：`page=1` / `next` / `prev` / `auto` / `status` | 手边有电脑时 |
| **MQTT 下行** | `{"page":1}` / `{"page":"next"}` | 远程 |

**线程安全红线**（这是设计要点，不是实现细节）：
LVGL **不是线程安全的**，而三个入口分别来自 core0 的 `console`/`net` 任务。
所以它们**只写一个原子变量**，真正调 `lv_tabview_set_act()` 的
**只有 core1 的 `gui_tick()`** —— 和 LVGL 的其它调用在同一条任务上，天然串行。

**顺便修的 bug**：第一版自动轮播"永远停在数据页"（每 10 秒都打
"切到页面 0"）。原因：轮播改了 `cur` 但没同步 `want`，下一拍
`want != cur` 又被判成"手动请求"，立刻切回。
⇒ 两条分支都**同时更新 `want` 和 `cur`**。

### 4.4 屏点亮：5 个坑（含一个"看起来像镜像"的字节序陷阱）

TFT_eSPI 在 Arduino-ESP32 **2.0.17** 下 `init()` 必崩
（`StoreProhibited`，`EXCVADDR=0x10`）—— 该库为速度**直接操作 SPI 寄存器**，
与核心版本不兼容。⇒ 换 **LovyanGFX**（自带 ESP32-S3 的 SPI 驱动，
走 esp-idf `spi_master`，不依赖 Arduino `SPIClass`）。

**最坑的一个**：`LV_COLOR_16_SWAP=1` 时 LVGL 已经交换过字节序，
我又把缓冲转成 `lgfx::rgb565_t*` → **转换两遍** → 横向条纹 + 发白。
而**条纹看起来非常像"镜像"**，导致我长时间误判成"旋转不对"，
在 `setRotation` 上试了一整天。

**最后怎么定死的**：不再问"文字是不是反的"（字节序错/镜像/旋转三种问题下
文字看起来都像反的，人眼分不开），而是**枚举 MADCTL 寄存器的 8 种组合**，
每种在屏上画**几何标记**（左上角方块 + 绿线在上 + 蓝线在左 + 大字编号），
让用户回答"哪一张方块在左上角" —— **几何位置是客观的**。

**教训**：**诊断要用客观判据，不能用主观感受。**

### 4.5 波形页"曲线是直线"的两层原因

第一层：Y 轴固定 ±20000，而振动波动只有 ±200 → 只占屏高 0.5%。
第二层（关键）：**三个轴的均值差太远**（`ax≈-10700`、`ay≈-10500`、
`az≈+6350`，都是重力），三条线各占 Y 轴一端、**永不交叠**；
范围要容下三个均值就必然压缩波动。

⇒ **"共用一根 Y 轴"和"显示波动"在数学上互斥**，只能二选一。
解法：**去均值显示**（`v - 本轴均值`），并加阈值自动切换 ——
剧烈振动时回到原始值以保留方向信息。

### 4.6 看门狗分级

- **F411**：IWDG ~2s（硬件看门狗，独立时钟源）
- **ESP32-S3**：`esp_task_wdt` 5s + `panic=true`

踩到的坑：**长周期任务不喂狗** → `vTaskDelayUntil(10000ms)` 一次睡 10 秒
直接触发复位（`task_wdt: - mb_fast (CPU 0)` + `rst:0xc`），而且它自己的
第一行日志都来不及打，看着像"任务卡死"。
⇒ 改成按 500ms **切片睡眠**，每片喂一次。

### 5.1 4 小时长跑实测明细（2026-10-09 10:28 ~ 14:28）

**这是"长时间稳定性"的硬证据**，也是对"485 已经 100%"的独立复验
（此前 870 次事务只代表几分钟，长跑才能暴露缓慢劣化）。

**主站（ESP32-S3）侧：**

| 指标 | 数值 |
|---|---|
| 事务总数 | **47510** |
| 成功 | **47510** |
| 超时 / 重试 / CRC错 / 异常码 | **0 / 0 / 0 / 0** |
| **首试成功率** | **100.00%** |
| 复位 / panic / 看门狗告警 / 节点离线 | **0 / 0 / 0 / 0** |
| **内部堆** | 起 89652 → 终 **89652** 字节（**净变化 0**，最小值也是 89652） |
| 队列深度 | 平均 0.02，**最大 1**（481 个采样点） |

**从站（STM32F411）侧**（2625 个统计点，起→终增量）：

| 指标 | 增量 | 说明 |
|---|---|---|
| 接收事件 `rx` | +43296 | 与主站事务量同量级 |
| **队列溢出 `drop`** | **0** | 接收队列（深 4）从未溢出 |
| **静默丢弃 `parse0`** | **0** | 协议层零丢帧 |
| 零长度帧 `0len` / 超长帧 `long` | **0 / 0** | 没有半截帧或截断 |
| 待处理 `q` | 恒 0 | 处理速度始终跟得上 |
| 连续运行 | t=3217s → **t=17618s**（4.9 小时无复位） | 启动时间早于本次测试 |

**结论**：
1. **总线可靠性是"稳态 100%"，不是"侥幸 100%"** —— 4 小时 4.7 万次事务零抖动
2. **零内存泄漏**（89652 字节 4 小时一动不动，连碎片波动都没有）
3. **生产-消费平衡**（队列最大深度 1，说明没有积压趋势）
4. **双看门狗工作正常**（两侧都 0 次触发，说明没有任务超时）

> 💡 **为什么这个测试值得做**：内存泄漏、队列积压、偶发丢帧这类问题
> **短测一定发现不了**。870 次事务的"100%"可能是运气；
> 47510 次、4 小时、两侧计数器一致，才能说"稳态可靠"。
> 面试时这个数字比"我调通了"有说服力得多。

1. **能拆到 PC 上验证的绝不留给联调** —— CRC 用 Python 对拍、

2. **改任何参数前先建立可量化的基线** —— 否则"改好了"只是感觉

## 7. 已知限制（诚实清单，面试加分项）

| 限制 | 影响 | 修法 |
|---|---|---|
| 舵机 PWM 实际落在 PA0（非代码注释里的 PA5） | **舵机不可用**；PA0 与板载 KEY1 冲突 | CubeMX 把 RS485_DE 挪到 PA1（PA5 让给 TIM2）——见 `docs/01` §4.1 |
